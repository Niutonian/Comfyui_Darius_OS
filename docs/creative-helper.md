# Creative chat and explicit prompt transfer

Ordinary project, Canvas and fullscreen voice conversations now develop ideas, scripts, art direction and prompt text. A request containing “generate” does not route to a workflow planner. The selected board is read-only context; sending a message never saves its draft. Voice transcription uses the same reply endpoint. Local gallery and media playback commands remain available.

The server calls the selected model with the `creative-helper` policy and no tools. This path returns before workflow discovery, visual planning, checkpoint execution or automatic rendering. Provider tool calls are rejected without dispatch. Legacy generation proposals are retained only as inert prompt text. Comfy assistant dispatch rejects mutations for conversation tasks, including direct dispatcher calls. The legacy chat queue boundary rejects submission, conversation-associated action proposals cannot be created, and old unsubmitted chat proposals cannot be approved. Existing jobs and previously queued approvals remain intact. The old conversation `/plan` endpoint returns 410. Explicit board Generate routes and workers remain unchanged.

## Interaction

Complete prompts use inert fenced text (`prompt` plus an optional short title). Valid blocks receive Copy and Use in board. Explanations remain outside the card; multiple alternatives have separate actions. Malformed or plain replies still support selecting text, or using the reply, then reviewing/editing it in the picker. Streaming output has no transfer action until saved as a completed reply.

Use in board lists the current project's unarchived boards. Its target review names the registered destination and shows any existing text before an explicit Replace prompt. Image recipes receive their active user prompt; MOSS/FIBO receive `globalPrompt` before layout compilation; H3 receives only its active mode's Scene and action prompt. No mode, camera/audio field, reference, region, workflow, model, seed, resolution or duration is changed. Applying never generates and does not create boards implicitly.

Apply uses a fixed source message/draft/text snapshot, project and board identity, destination, board/document revisions and a durable idempotency UUID. The server rechecks ownership, current mode, archive status and revisions within one transaction. Conflicts retain the candidate text and require Refresh target review. Repeated network requests with the same transfer identity do not create extra revisions. A different request cannot reuse that identity. The existing project event stream synchronizes edits to other devices.

Each transfer records its old/new text and source references in project events, with an explicit Undo action. Undo only succeeds while the destination and both revisions still match; it cannot roll back another device's later edit. Repeated Undo is inert. Local unsaved board edits block transfer until saved or reloaded; edits typed while Apply is in flight are retained by the editor's normal conflict handling. Queued/running generation snapshots and output selections remain unchanged.

Chat retains the existing project conversation and bounded context: recent turns, earlier turn excerpts, editable project notes, characters, scenes and shots. Board selection does not start another conversation or replace the project discussion. Explicitly attached/pinned project images retain bounded visual previews where the selected model supports vision. There is no new memory engine or claim of unlimited history. Suggestions in history remain attributed conversation text; later corrections take precedence in the helper instruction.

## Validation

Focused tests cover the eight text/media request regressions, all five provider transports, execution dispatcher/queue rejection, all board families, exact prompt-only edits, idempotency, ownership, mode/archive/revision conflicts, field limits, Undo, and plain-text selection. Frontend tests exercise review, Copy, edits, conflicts, empty lists, unsaved local drafts, network retries and the absence of old chat execution controls. Release checks and browser evidence are recorded separately under ignored `data/`.

Current checks: 273 frontend tests, TypeScript, changed-file lint and the production build passed. A focused backend run covering the new capability/transfer paths, Canvas recipes, existing recovery and conversations passed 245 tests; the latest helper-only run passed 25, including the CLI's own denied-tool policy. Desktop and phone acceptance used a separate database and a deterministic text provider, applied exact prompts to MOSS/FIBO boards and opened their editors with zero jobs. Evidence is in `data/creative-helper-review/`; these were interface/integration checks, not live model-quality or GPU benchmarks.

The complete pre-migration backend run is not green: it retains legacy tests requiring chat execution, alongside 944 passing checks. Those old tests remain available; the local-render test file was restored byte-for-byte from the earlier private snapshot after automatic approval review rejected a broad rewrite that could remove execution/recovery coverage. Migration must retain equivalent explicit board generation, worker and recovery coverage. This remains a release-verification blocker; the source is not cleared for publication by the focused checks alone.
